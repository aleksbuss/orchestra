## 💾 Data Layout (`data/`)

Orchestra has no traditional database — `data/` IS the database. Every directory is a separate concern; treat them as schemas.

**Data root resolution (PM #62) — single source of truth.** The data root is **`getDataDir()` / `dataPath()` from [`src/lib/storage/data-dir.ts`](../../src/lib/storage/data-dir.ts)**, which honors the `ORCHESTRA_DATA_DIR` env var (absolute or cwd-relative; defaults to `<cwd>/data`). **Never write `path.join(process.cwd(), "data")` anywhere** — always go through the resolver; a fresh hardcoded literal is a defect (grep for `process.cwd(), "data"` in review — it must return only `data-dir.ts`). To isolate a test/dev/E2E run, set `ORCHESTRA_DATA_DIR` to a throwaway dir — **NEVER `mv`/`rm` the live `data/`** (PM #62 lost 34 real chats doing exactly that). Playwright is wired this way already: `playwright.config.ts` + `tests/e2e/global-setup.ts` run the whole suite against `.e2e-data`, leaving the real `data/` untouched. **Two isolated roots, not one (PM #103):** `.e2e-data` is SEEDED (the operator's real settings.json is copied in, plus an `auth:reset`) so model-dependent specs have working providers locally, while `.e2e-clean-data` is created empty and seeded with NOTHING — it backs a second dev server on its own port and its own Next `distDir`, and it is the only place the first-run path is exercised the way a stranger meets it. Constants for the second one live in [`tests/e2e/clean-boot-env.ts`](../../tests/e2e/clean-boot-env.ts); **never add seeding to it** — the seeding is what makes `.e2e-data` unable to answer "does a fresh install work?".

**Boot-warmed, route-read module state MUST live on `globalThis` (PM #71).** Next.js bundles `instrumentation-node.ts` and the API route handlers into SEPARATE module graphs, so a module-level `let` warmed at boot (e.g. `refreshOpenRouterPricingCache()` from instrumentation) is a DIFFERENT instance than the one a request handler imports — the handler's copy stays empty. PM #71 was exactly this: the OpenRouter pricing cache showed `337 models priced` in `/api/health` (warmed instance) while every chat's cost banner read an empty map (route instance) and showed "cost unknown" for a year. Fix: store such state on a `Symbol.for(...)`-keyed `globalThis` singleton (one per process, shared across instances). Symptom signature to watch for: a cache `/api/health` reports as full but every consumer sees empty. Any new boot-initialized singleton (pricing, embeddings cache, model catalogs) follows this.

| `data-backups/data-<ts>/` (**sibling of `data/`, NOT under it**) | `storage/backup.ts` | Full-`data/` snapshots — boot + daily, `npm-cache`/`tmp`/`cache` excluded at the top level and regenerable dependency/build trees (`node_modules`, `.venv`, `.next`, …) excluded at any depth. Local-first data safety: `data/` has NO external redundancy, so a bad write / disk failure / `rm -rf data/` (PM #62) is otherwise unrecoverable. **Data-backup operator knobs + restore.** Auto-backup is wired at boot via `ensureDataBackupScheduled()` (`instrumentation-node.ts`): a boot snapshot + a recurring interval. **Boot-dedup (audit fix #1):** the boot snapshot is SKIPPED when a backup younger than half the interval already exists (`shouldRunBootBackup`), so frequent restarts don't thrash full-`data/` copies. **Observability (audit fix #2):** `/api/health` carries a `data_backup` subsystem (`getBackupStatus` — count + newest age; warns when STALE, i.e. backups exist but are older than 2× the interval, so a silently-stopped backup is visible instead of false safety; "no backups yet" is `ok`, not a fresh-install false alarm). Env: `ORCHESTRA_BACKUP_DISABLED=true` (strict-string opt-out), `ORCHESTRA_BACKUP_DIR` (default `<data>/../data-backups`), `ORCHESTRA_BACKUP_RETENTION` (default 7), `ORCHESTRA_BACKUP_INTERVAL_HOURS` (default 24). Skipped under `VITEST`/`NODE_ENV=test`. **Restore is deliberately MANUAL** (it overwrites live state): stop the server, then `rm -rf data && cp -r data-backups/<data-…> data`. **A restore does NOT bring back dependency trees** — since 2026-08 the copy skips `node_modules` / `.venv` / `venv` / `__pycache__` / `.pytest_cache` / `.next` / `.turbo` / `.parcel-cache` at ANY depth, so a restored project needs `npm install` (or the equivalent) before it builds. That is the whole trade: measured on a real install, those trees were **677 MB of each 26 MB-of-actual-state snapshot — 96% of the bytes and 94% of the files** — reinstallable from lockfiles that ARE in the backup, and the ring fell from 4.6 GB to 0.18 GB. The list is deliberately conservative: `.git` is NOT skipped (a project's history is frequently its only copy), and neither are `dist`/`build`, which are conventionally output but hand-authored often enough that skipping them could lose work silently. The backup dirs are plain, timestamp-sortable copies — inspect with `ls data-backups/`, no tooling needed. Backups are LOCAL (no egress) so Privacy Mode doesn't gate them. NOT in scope by design: compression, incremental/dedup, offsite/cloud, encryption, point-in-time consistency — over-engineering for a solo local tool; per-file atomicity (every JSON written via `safeWriteFile`) makes each copied file self-consistent, which is sufficient for the loss-not-tearing threat model.

**Restore drill — EXERCISED 2026-08-11, not just documented.** The procedure above had never actually been run. It has now, against a real 770 MB snapshot (66 chats, 10 project dirs), restored into a throwaway dir rather than over live state:

```bash
# 1. Restore into a THROWAWAY dir first. Never rehearse over the live one.
cp -r data-backups/data-2026-08-09T08-30-55-312Z /tmp/restored     # 17s, 770 MB

# 2. You will not know the restored password if the backup predates your last
#    credential change — reset auth SCOPED to the copy.
ORCHESTRA_DATA_DIR=/tmp/restored npm run auth:reset                # → admin/admin

# 3. Boot against it. ORCHESTRA_BACKUP_DIR must be overridden too, or the boot
#    snapshot lands in the REAL ring (`backupRoot()` derives from `<data>/..`).
ORCHESTRA_DATA_DIR=/tmp/restored ORCHESTRA_BACKUP_DIR=/tmp/restored-backups \
  npm run dev -- -p 3006
```

Result: `/api/health` **healthy**, zero errors in the boot log, `chat_index_integrity` consistent, 66/66 chats indexed, a real chat opened with its messages intact, projects listed. The recovery path works.

Two things the drill measured that reading could not:

- **The `node_modules` exclusion is real, not aspirational.** The restored instance's own boot snapshot came out at **33 MB from a 770 MB source with zero `node_modules` trees** — a 23× reduction on live data. (Snapshots taken before 2026-08 still contain those trees; the ring only shrinks as they rotate out.)
- **`getAllProjects()` enumerates by scanning `data/projects/*/` and reading `.meta/project.json`, silently skipping any directory without it.** In this data, 4 of 10 project dirs have `.meta/mcp` + `.meta/skills` but NO `project.json` — so they are invisible in the app while their files sit on disk (one of them holds 252 MB / 16k files). This is NOT a restore defect: live and restored agree exactly, so the condition predates the snapshot. It is recorded here because a restore is exactly when someone counts their projects and finds fewer than they expected.

**Schema versioning — stamp + defensive load (NOT a migration engine).** [`storage/schema-version.ts`](../../src/lib/storage/schema-version.ts) holds `CURRENT_SCHEMA_VERSION` + `stampSchemaVersion()` / `warnIfFutureSchema()`. On WRITE the persisted JSON is tagged with the version; on READ a record written by a NEWER build (`schemaVersion > CURRENT`) triggers a LOUD warn — the dangerous direction, because the older code drops fields it doesn't understand on the next save (lossy downgrade round-trip). Recovery from a detected downgrade is `data-backups/`, NOT an auto-migration (deliberate — over-engineering for a solo local tool). The stamp is a persistence-ENVELOPE field, never a domain-type field: chat-store's Zod `ChatSchema` strips it on read; settings-store strips it explicitly. **Wired today on the two highest-value stores:** chats (`chat-store.ts` — stamp in `flushNow`, warn in `getChat`) and settings (`settings-store.ts` — stamp in `saveSettings`, warn+strip in `getSettings`). **To add a new store:** `stampSchemaVersion(record)` at its single serialize chokepoint + `warnIfFutureSchema(parsed, label)` at its parse chokepoint — two one-liners. **Bump `CURRENT_SCHEMA_VERSION` ONLY on a backward-incompatible change** (field renamed/removed/re-typed); additive optional fields are forward-compatible and need no bump. Regression: [`schema-version.test.ts`](../../src/lib/storage/schema-version.test.ts) (unit + a real chat-store round-trip proving the stamp lands on disk and a future-stamped file loads clean while warning).

**Settings defaults are credential-aware on read, not frozen at install (PM #101).** `DEFAULT_SETTINGS` still literally ships `openai/gpt-4o`, but every return path of `getSettings` passes through `withResolvedDefaults` → [`applyCredentialAwareModelDefaults`](../../src/lib/storage/fresh-install-defaults.ts), which retargets the chat + utility slots at whichever provider the operator actually holds a key for (vault first, then the provider's `envKey`; priority OpenRouter → Anthropic → Google). **Three properties to preserve if you touch this:** (1) it fires only while the chat slot is byte-identical to the shipped default — provider, model id, and no inline key — so it can never overwrite a chosen model; (2) it is on the READ path deliberately, which is the only way one implementation covers both "key pasted into the vault after first boot" and "key that only ever lived in `.env.local`"; (3) `saveSettings` reads through `getSettings`, so the first write of any kind persists the overlay — intended, because at that point it stops being a derived default and becomes stored configuration. `embeddingsModel` is deliberately NOT retargeted (OpenRouter has no embeddings API). Adding a provider to `STARTER_MODELS` requires its ids to exist in `STAR_MODELS` / `LIGHT_MODELS` — a test enforces the coupling.

**Why this is NOT speculative gold-plating (audit fix #5 — resolved as keep-and-cap).** A skeptic rightly asks "`CURRENT_SCHEMA_VERSION` is 1 and stays 1 until the first breaking change — is the stamp YAGNI?" No: it is the cheap DETECTION half of the data-safety pair whose RECOVERY half is `data-backups/`. The detection has value the moment it ships — the day you `git checkout` an older build (or run two machines on different versions) against newer data, the loud `console.warn` (which the local operator sees in their own `npm run dev` terminal — adequate visibility for a solo tool, no APM/health-subsystem needed) tells you to restore from a backup BEFORE the older code's next save silently drops fields. The cost is two one-liners per store + a stamp on write. **Deliberately CAPPED — do NOT expand into:** an auto-migration engine, a `/api/health` schema subsystem, or per-store proliferation beyond the two highest-value stores. If a future change is genuinely backward-incompatible, the response is "bump the version + (if needed) a one-off transform at that store's read chokepoint," not a framework.

When you add a new persistent surface, add a row here in the same commit (Critical Rule §7) AND state the retention strategy — one of (a) sweeper in `cron/sweepers.ts`, (b) "never auto-swept — user data" with reasoning, (c) atomic cleanup tied to a higher-level deletion, or (d) self-pruning ring buffer like `snapshots.ts`. Don't ship an unbounded directory.
